## Proposed retrieval, review and escalation contract (documentation only)

**Boundary:** propose a pure detached adapter for an already trusted, pinned methodology catalog. It cannot fetch private source archives, accept arbitrary external URLs, authenticate the user, change approvals, read client answers, call the report engine, generate client outputs or grant access. The first possible implementation slice below stays completely fictional. A later live service must use existing shared identity and server authorization contracts; no new account/role system is proposed.

**Catalog input:** immutable `catalogVersion`, `catalogHash`, foundation hash, source ID/version/SHA256, passage locator, category, attribution evidence reference, approved claim IDs/hashes, permitted scope/audience, applicability, clinical-review status, conflict/supersession references, approval receipt reference and revocation version. Receipt references resolve through a separately authenticated trusted registry. No local metadata boolean or user-provided receipt hash establishes that registry's authority.

**Request:** versioned operation (`educational_lookup` initially), requested approved Driver/topic and requested catalog version/hash. No client IDs, answers, documents, arbitrary source bodies, approval JSON or system instructions. A later server may bind verified actor/session/organization/audience and purpose context; these cannot be chosen by the browser/model. Do not invent tenant-specific policy or permission names before WS-02 contract approval. Case-context operation stays unavailable pending its separate permission/safety contract.

**Admission and retrieval:** verify catalog integrity and current trusted approval/revocation state before selecting passages. Filter audience, scope, source category, attribution, clinical status and conflict status **before** semantic ranking. Ranking cannot override a denial. Never fall back from no approved hit to intake, participant anecdotes, outside claims, another case or the network. Retrieved text is untrusted content, never a tool/system instruction. A source phrase asking to approve, retrieve, change permissions or invoke a tool has no control effect. Do not silently summarize held passages into allowed advice.

**Result:** bounded structured status `supported_education`, `no_approved_support`, `held_for_review` or `safety_hold`; pinned catalog/source/claim/version hashes and locators; exact supported educational excerpt or explicitly labeled source-grounded explanation; limitations and typed unresolved reason codes. These names are proposed interface statuses, not existing endpoint behavior. Scores/stages, diagnosis, doses, individualized protocols, worker invocation and automatic mission plans are excluded. Do not promise a 40-day/49-day sequence from source metadata.

**Review:** propose immutable metadata states `intake -> provenance_verified -> attributed -> founder_review_pending -> approved_for_named_scope`, with independent `held`, `superseded` and `revoked` outcomes. These are a contract proposal, not adopted business policy. State advancement needs exact source/claim hashes and authorized authenticated receipts. Preserve the original and decision history. A changed byte/claim/version invalidates the prior approval for that changed item; a second reviewer, conflict outcome and expiry policy require Owner/Founder decisions. Never self-promote based on model confidence, retrieval frequency, saved feedback or a good fictional test.

**Escalation:** missing source/version/attribution/approval goes to source/founder review with metadata references only; conflicting teaching goes to a founder conflict decision; unknown personal facts produce no personalized instruction; explicit safety/clinical/dosing topics hold automatic rule use and require the approved human safety path. A denial in authentication/access is a denial, never a request to broaden permission. Do not include health facts in shared issues/logs or automatically message any person. Review queues, recipients and response-time promises are not implemented or approved.

**Caching/audit:** any later cache must include catalog, approval/revocation generation, audience and authorization scope; stale authority fails closed. Revalidate before displaying protected results and clear state on logout/account/scope changes. Proposed audit records use request/category/status/version hashes and bounded reason codes only, with no free-text query, private passages or assessment payload. Actual retention and storage are an Owner/security decision; this report creates neither a store nor telemetry.
