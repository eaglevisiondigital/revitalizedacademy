## Proposed financial event contract v0 — review only

This is an interface proposal for WS03/05/08/09/10 discussion, not approved architecture or executable implementation. Keep one identity model and reuse existing finance sources. Exact physical schemas/API names await shared ownership clearance.

Common envelope: contract version, immutable event UUID, event type/schema version, producer and organization/legal-entity ID, server recorded timestamp and business occurrence time, correlation/causation ID, source object/version, route/provider/environment, actor category/reference, policy version/effective date, evidence reference/digest and deduplication key. Evidence digests cover approved nonsecret business payload only; never credentials, health data or bearer tokens. Amounts use integer minor units plus explicit ISO currency; points use a separate typed integer unit. No floating point, cross-currency netting, client-submitted settlement or mixed sandbox/live evidence.

| Event family | Authoritative producer / prerequisites | Effect and idempotency proposal |
| --- | --- | --- |
| Application/agreement/profile | Identity/affiliate service; actual signer and agreement hash | Immutable accepted version; uniqueness by actor/agreement version; eligibility is not earnings |
| Campaign/link/click/consultation | Approved campaign service and CRM; consented link/campaign revision | Minimal attribution evidence; click UUID dedupe, bot/duplicate markers; no commission from click/booking |
| Settlement verified | WS09 independently verifies original provider transaction, entity, mode, amount, currency and enrollment reference | Unique provider/entity/mode/transaction/settlement version; unresolved mismatch quarantined |
| Earning proposed/held | Compensation service consumes verified settlement and valid single-level rule snapshot | Unique qualifying event + beneficiary + rule component + period; no recursive upline and no payable credit yet |
| Earning released | Finance authority after approved hold/dispute checks | Append-only balanced cash-liability posting; unique held earning/release decision; exact account/currency |
| Credit or point earned/redeemed/expired | Separate unit-specific rule and redemption authorization | Independent nonwithdrawable subledgers; atomic reserve/consume; unique award or redemption command |
| Bonus/refer-X-get-Y qualification | Distinct eligible-event set, approved rule version/cap | One award per threshold instance; corrected qualification emits compensating event |
| Refund/void/chargeback/correction | Finance verifies original provider reference; approved accounting rule | Append-only reversal linked to original posting; never mutate historical paid invoice or delete ledger |
| Dispute opened/resolved | Authenticated scoped reviewer with reason/evidence | Hold affected balance; resolution references immutable decision; no automatic status-to-payout shortcut |
| Payout requested/reserved/submitted | Approved provider/account and eligible reconciled cash only | Atomically reserve liability; idempotency by entity/provider/environment/request UUID |
| Payout succeeded/failed/uncertain | Signed provider event plus independent readback | Success settles once; uncertainty retains reservation/no retry; confirmed failure permits separately controlled retry |
| Reconciliation close/exception | Finance aggregate comparison of provider, clearing, liability, payout and invoices | Append-only discrepancy case and signed close snapshot; cannot fabricate missing financial events |

Proposed earning states: ineligible or proposed → held → releasable → reserved → paid; disputes and provider uncertainty freeze affected transitions. Reversals are new linked postings. The final allowed transitions, hold periods, refund effects, accrual method, accounts and actor separation require A04–A15 approval; these state labels are a review aid, not business policy.

Conservation proposals: each journal balances within entity/currency/unit; reserved cash cannot exceed eligible reconciled cash; one settled event cannot be awarded twice under the same approved component; identical replay is a no-op, changed payload with reused key is a conflict; recurring periods have stable IDs. Rebuild read models from immutable accepted events and compare to provider totals; prohibit direct balance editing. Financial document retention is independent from optional marketing data; legally required exceptions must be approved, never inferred.
