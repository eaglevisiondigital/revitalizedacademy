## Narrow worker identity

Selected design: a **purpose-restricted application sealing identity**, not a new PostgreSQL/Auth login. `roadmap-processing` no longer reads or falls back to `SUPABASE_SERVICE_ROLE_KEY`. A custom SQL login was rejected here because default PUBLIC privileges/inheritance need a broader project-wide audit and direct credential provisioning; a modern Supabase secret key still maps to service_role and would not narrow authority.

Protected names, production Netlify site `ece0f6f3-6c3d-46e6-bb51-95ce1ccefb06`, Functions scope, Production context only:

- `ROADMAP_PROCESSING_SEAL_KEY_ID` — UUID of the private credential slot.
- `ROADMAP_PROCESSING_SEAL_SECRET` — newly generated cryptographically random32-byte value, encoded64 lowercase hex characters. Never a database password, JWT signing key, service-role key or client answer.

The worker retains the genuine founder JWT and public application key for all RPCs. It claims only that founder's authorized source job and computes the existing evidence draft server-side. A founder-authorized RPC supplies a canonical, versioned challenge binding key/batch, source fingerprint, engine pins, actor/session, exact grant, job/lease, document hash and expirations. The worker signs it using HMAC-SHA256. A second authenticated RPC verifies the same current gates, fixed-length proof, private key, source and lease; then reuses every existing document/null-score validation. Its domain-separated finish capability is stable across identical retries. The original finish path rechecks live key/batch before storing a new immutable version.

The secret never appears in the browser, a JWT, SQL proof call, returned challenge, response or source artifact. The DB stores it only in a private ACL/RLS-protected configuration table; this is not a claim of separate application-level encryption. Supabase storage/administrator security still applies. Revocation erases it while retaining its configuration digest/audit. Only bound active keys work; a staged key cannot access sources or seal anything. A key by itself cannot bypass RLS, read tables, run processing, impersonate a founder or sign other API operations. The new public challenge/seal RPCs grant EXECUTE only to authenticated and independently require designated-founder authorization; anonymous, members, Coaches, nonfounder Owners/Admins and service-role calls fail. All operator helpers deny browser/service roles. Netlify Functions scope is site-wide: it is not per-Function isolation. The purpose/session/source gates limit what that credential can do even if another Function could read its environment.

The worker archive changes only the tenth Function. The other nine archives are retained byte-for-byte, not rebuilt; Node22/runtime/config/routes and the existing payment-worker schedule remain pinned. No new Function or scheduled worker is introduced. Canonical production origin restrictions remain exact; an unpublished permalink cannot prove genuine founder acceptance.
